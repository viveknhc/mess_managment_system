1. Fix before the first client goes live

Problem: Three nightly tasks are written but never scheduled: mark subscriptions EXPIRED, generate next day's deliveries, and send "expiring soon" notifications. CELERY_BEAT_SCHEDULE in config/settings/base.py only has the two platform billing tasks. docker-compose.yml has no Celery worker or beat, and render.yaml only runs the web API.

Effect on the plans: "Expiry tracking" and "In-app notifications (expiry)" would only half work. Old subscriptions stay ACTIVE past their end date, and no expiry alerts appear.

Fix: Add the three tasks to the beat schedule. Run a worker and a beat process wherever you deploy. Rough estimate: half a day, plus a test.

Problem: Creating staff skips the quota check. StaffViewSet.perform_create in apps/accounts/views.py overrides the base method that calls check_quota. So "Up to 3 / Up to 10 team logins" is not enforced.

Careful: check_quota counts every user of the business, including customer portal logins. Staff must be counted by staff roles only, or Premium portal customers would use up the limit.

Fix: Call the check in staff creation with a staff-roles-only count, and add a test. Rough estimate: 2 to 3 hours.

Problem: The customer limit counts all customer records, including inactive and blocked ones. The plans say "Active customers".

Choose one: change the plan wording to "Customers", or change the count to ACTIVE customers only. The second is friendlier to clients and takes about an hour.

Problem: Limits only apply when a business has a plan assigned. With no plan (or in trial) everything is unlimited.

Fix: Create Basic (50 customers, 3 logins), Standard (200, 10) and Premium (0 = unlimited, 0 = unlimited) as platform plans. Assign one to each client's business at setup. A small management command makes this repeatable.

Problem: docker-compose.yml is for development only: Django runserver, the Vite dev server, no Celery, no HTTPS. render.yaml deploys only the API for Render.

Needed: A production compose file with gunicorn, the built frontend served by Nginx or Caddy, PostgreSQL, Redis, Celery worker and beat, HTTPS, and an .env template. Plus a short "deploy to a new client server" checklist. Your plans promise "deployment on your server", so this is the core delivery.

Problem: The audit log table and AuditService.log() exist, and there is an admin view. But no code in subscriptions, payments, deliveries or staff calls it. Only the demo seed command writes entries. The tracker marks AU-02 (write hooks) done, but it is not.

Fix: Call AuditService.log() from the services on subscription changes, payments, delivery status changes and staff changes. Add tests. Otherwise take "Audit log" out of Premium. Rough estimate: half a day.

Problem: The settings page saves skip rule (extend / credit / none), max skip days, delivery time window and the notification preferences, but nothing reads them. A code comment says "Settings module will add EXTEND/CREDIT". Only min/max pause days are used (in the customer portal).

Fix: Make a skip extend the end date or add a meal credit, enforce the max skip days, show the delivery window on the delivery list, and respect the notification switches. Or remove those fields from the plans and the screen until they work. Rough estimate: 1 to 2 days.

Problem: Only "subscription activated" and the nightly "expiring soon" (which needs the scheduler) are sent. "Payment received" is written but never called, and there is no delivery notification. Notifications go to the owner only.

Fix: Call the payment-received notification when a payment is recorded, add a delivery update notification, or reword the plans to "activation and expiry alerts". Rough estimate: 2 to 3 hours.

Problem: The API has customers, subscriptions, revenue, meals and payments reports. The screen only shows revenue, subscriptions and meals.

Fix: Add the customers and payments reports to the page, or say "3 reports" in the plans. Rough estimate: 3 to 4 hours.
