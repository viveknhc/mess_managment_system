1. Fix before charging the first client

Problem: Only the platform billing check is in CELERY_BEAT_SCHEDULE (config/settings/base.py). Three tasks are written but never scheduled: mark subscriptions EXPIRED, send "expiring soon" alerts, and generate next day's deliveries. render.yaml runs only gunicorn, with no worker, scheduler or Redis.

Effect: "Subscription tracking with automatic expiry alerts" doesn't happen. Subscriptions stay ACTIVE past their end date. Overdue businesses are never moved to PAST_DUE or SUSPENDED.

Fix: Add the tasks to the beat schedule, or (cheaper on Render's free tier) add management commands and call them from a daily cron. Add a test for each.

Problem: SignupPage and BillingPage call /signup/ and /billing/checkout/, which the backend no longer has (frontend/src/features/platform/platformApi.ts:102,125). BillingPage reads available_plans, which the API no longer returns. e2e/02-platform-billing.spec.ts still tests signup and trial.

Effect: Owners see errors on the Billing page, and CI's E2E job fails.

Fix: Remove the signup flow and rebuild BillingPage to show plan, paid-until, amount due, payment history and a Cancel button. Update the frontend types (setup_fee, reactivation_fee, PENDING status) and the E2E spec.

Problem: The backend endpoints POST platform/businesses/{id}/record-payment/, /cancel/ and POST platform/businesses/ exist and are tested, but no page calls them. BusinessesListPage shows "Trial Ends" instead of paid-until and amount due. The Plans page can't edit the setup or reactivation fee.

Effect: You can't collect ₹3,000 / ₹500 / ₹1,000 or onboard a new mess from the app. On Render's free tier there's no shell, so only curl works.

Fix: Add the forms and columns to the platform pages. Remove the leftover "On Trial" card from the platform dashboard.

Problem: A new business starts ACTIVE, and a PENDING (never paid) subscription is never suspended by run_billing_checks.

Effect: A mess can use the app free forever without paying the ₹3,000.

Fix: Either keep new businesses blocked until the first payment is recorded, or give them a short grace period and then suspend. Add a test.

Problem: Suspension is only checked in TenantScopedViewSet (common/viewsets.py). The dashboard, reports, settings and customer-portal views are plain APIViews and don't check it.

Effect: A suspended business can still use the dashboard, reports and portal.

Fix: Move the check into a shared permission class used by every tenant endpoint. Add a test per view.

Problem: The super-admin Reactivate action (services.py, reactivate) restores access with no payment. The fee only applies through record-payment.

Effect: The "₹1,000 reactivation fee after 3 months" term can be bypassed.

Fix: Reactivate only through a recorded payment, or have Reactivate require one when more than 3 months have passed.

Problem: render.yaml sets SEED_DEMO: "1".

Effect: The "Annapurna Mess" demo data is loaded into the live database.

Fix: Set it to "0" before the first real client.

2. Promised in the PDF but missing

Problem: There's no CSV or Excel import anywhere in the backend or frontend. The Monthly Plan has max_customers = 0 (unlimited), so a 100 limit isn't enforced either.

Effect: The setup fee promises this import.

Fix: Add a CSV upload (name, phone, address, notes) with row-level errors and a 100-row cap per import. Or import by script during setup and keep it internal.

Problem: docs/db_backup_restore.md covers manual pg_dump only, and its docker commands use the service name postgres while docker-compose.yml calls it db.

Effect: "Daily data backup" is promised.

Fix: Schedule a daily pg_dump to off-site storage, or rely on Neon's point-in-time restore (check its retention). Test a restore once, and fix the runbook.

Problem: CONTACT_WHATSAPP = '910000000000' is a placeholder (LandingPage.tsx). There's no support email anywhere. The suspended banner says "contact support" with no number or link, and there's no Help entry in the admin menu.

Effect: "WhatsApp and email support" has no working contact.

Fix: Set the real number, add a support email, and add a Help/Support link in the app and on the suspended banner.

Problem: Alerts are in-app only (notifications/services.py: "IN_APP channel for now"). No email settings exist in config/settings, so there's no email or WhatsApp sending.

Effect: Owners only see alerts if they open the app. Customers get none.

Fix: Fix the background jobs first. Then add email (SMTP settings) and later WhatsApp if needed.

Problem: Owner pause only changes the status and leaves deliveries on the daily list. Portal pause puts the subscription in PAUSED even for a future window, with no auto-resume. DeliveryService.resume_deliveries is never called, so resuming doesn't restore deliveries. End date isn't extended for paused days.

Effect: Delivery staff can see paused customers, and resumed customers can miss meals.

Fix: Cancel deliveries in the range on owner pause, restore them on resume, auto-resume when the window ends, and decide whether to extend the end date.

Problem: The PDF says breakfast, lunch, dinner, tiffin. The app's default meals are Breakfast, Lunch, Dinner, Snacks, and the landing page says "packed meals".

Effect: Small mismatch a client may notice.

Fix: Pick one word and use it in the PDF, landing page and default meals.
